## ۱. هدف بررسی (Audit Objectives)

هدف بنیادین از این ممیزی، **استخراج دقیق، علمی و بدون ابهام خط پایه عملکردی (Performance Baseline)** فرانت‌اند فروشگاه Paradox Shop بر روی **بیلد واقعی پروداکشن (Production Build & Standalone Runtime)** و تفکیک آن از داده‌های تاریخی و غیرواقعی محیط توسعه (`next dev`) است.

در این فاز:
- هیچ‌گونه تغییر معماری، بازنویسی کامپوننت، حذف ویژگی‌ها یا دستکاری سیستم طراحی انجام نشده است.
- عملکرد فرانت‌اند دقیقاً به همان صورت که در بیلد پروداکشن و کانتینر داکر اجرا می‌شود ارزیابی شده است.
- خطاهای ناشی از ابزارهای مانیتورینگ توسعه و رندرهای شبیه‌سازی‌شده تفکیک شده‌اند.

## ۲. تفکیک محیط Development در برابر Production

بررسی مقایسه‌ای ساختار ارکستراسیون و کانفیگ‌های پروژه نشان‌دهنده تفکیک کامل لایه‌های توسعه و پروداکشن است:

| مولفه / شاخص | محیط توسعه (Development) | محیط پروداکشن (Production) |
| :--- | :--- | :--- |
| **فایل ارکستراسیون** | `docker-compose.yml` / `docker-compose.dev.yml` | `docker-compose.prod.yml` |
| **فایل داکرفایل** | `frontend/Dockerfile.dev` | `frontend/Dockerfile` (Multi-stage Build) |
| **دستور راه‌اندازی فرانت‌اند** | `npm run dev` (`next dev -H 0.0.0.0`) | `node server.js` (Standalone Output) |
| **وضعیت دایرکتوری `.next`** | Anonymous Volume (`/app/.next`) متصل به سورس لوکال | ایزوله کامل؛ نادیده‌گیری در `.dockerignore` و ساخت تمیز از صفر |
| **وب‌سرور معکوس** | دسترسی مستقیم پورت ۳۰۰۰ | Nginx Reverse Proxy (`shop_nginx_prod`) روی پورت‌های ۸۰ و ۴۴۳ |
| **دستور بیلد** | بیلد در حافظه / JIT Compilation بر اساس درخواست روت‌ها | `npm ci` و `next build` با کامپایل کامل SWC و بهینه‌سازی استاتیک |
| **متغیرهای محیطی** | `.env` محلی با `DJANGO_DEBUG=True` | تزریق امن `NODE_ENV=production` و ریدایرکت‌های بازنویسی باز |

### تحلیل احتمال آلودگی (Contamination Audit) دایرکتوری `.next`:
1. در فایل‌های `.dockerignore` ریشه و `frontend/.dockerignore`، دایرکتوری `.next` و `node_modules` به طور صریح مسدود شده‌اند.
2. در ایمیج پروداکشن `paradox-shop-frontend-prod`، استیج اول (`builder`) با اجرای `npm ci` و `npm run build` باندل کاملاً جدید تولید کرده و فقط پوشه‌های `.next/standalone` و `.next/static` و `public` را به استیج سبک `runner` منتقل می‌کند.
3. هیچ اشتراک فایلی بین محیط توسعه هاست و کانتینر پروداکشن وجود ندارد.

## ۷. تحلیل تفکیکی لایه‌های فرانت‌اند (In-Depth Technical Audits)

### الف) تحلیل جاوااسکریپت و باندل‌های کلاینت (JavaScript Bundle Analysis)
1. **حجم کد اشتراکی:** حجم کل جاوااسکریپت اشتراکی برای تمامی صفحات برابر با **87.4 kB** است که در مقیاس استانداردهای وب نوین بسیار بهینه و سبک محسوب می‌شود.
2. **بزرگ‌ترین چانک‌های انتقالی در روت‌ها:**
   - `fd9d1056-8f4fb286d28e1600.js` (حجم انتقالی Gzip: `54.1 kB` / حجم بازشده: `172.8 kB`) — شامل هسته React، React-DOM و کتابخانه‌های پایه رندر.
   - `5706-335090597993bcd7.js` (حجم انتقالی Gzip: `42.1 kB` / حجم بازشده: `129.5 kB`) — شامل کتابخانه‌های انیمیشن Framer Motion و استیت منیجرها.
   - `7023-f12473fc2d90334f.js` (حجم انتقالی Gzip: `32.1 kB` / حجم بازشده: `123.7 kB`) — کامپوننت‌های مشترک UI و Lucide Icons.
   - `7345-1ef6d243231ea5b1.js` (حجم انتقالی Gzip: `19.0 kB` / حجم بازشده: `50.4 kB`) — هسته ارتباطات API و TanStack Query.
3. **ارزیابی Unused JavaScript:** میزان صرفه‌جویی بالقوه جاوااسکریپت در تمامی صفحات کمتر از `22 KiB` گزارش شده است که نشان می‌دهد Tree-shaking کدهای Next.js به درستی عمل می‌کند.
4. **نشت کدهای ادمین به صفحات عمومی:** هیچ‌یک از کامپوننت‌ها، چارت‌های Recharts یا کدهای اختصاصی پنل مدیریت (`/admin`) به باندل‌های عمومی استورفرانت راه نیافته‌اند و تفکیک روت‌ها کاملاً رعایت شده است.

---

### ب) تحلیل ماژول سه‌بعدی و گرافیک وب‌جی‌ال (Three.js & WebGL Analysis)
1. **نحوه لودینگ:** کامپوننت `PenroseHero3D` با استفاده از `next/dynamic` با تنظیم `ssr: false` به صورت تنبل (Lazy) بارگذاری می‌شود و مانع از مسدود شدن SSR و HTML اولیه صفحه اصلی نمی‌شود.
2. **سربار در صفحات دیگر:** ماژول Three.js منحصراً در صفحه اصلی لود می‌شود و کاتالوگ، جزئیات، سبد خرید و پنل مدیریت هیچ وابستگی به این پکیج در کلاینت ندارند.
3. **دسترسی‌پذیری و بار پردازشی:**
   - مجهز به قابلیت Fallback برداری دو بعدی SVG در صورت عدم پشتیبانی مرورگر از WebGL.
   - رعایت استاندارد `prefers-reduced-motion` و توقف حلقه‌های رندرینگ چرخشی در دستگاه‌های با مصرف انرژی محدود.
   - آزادسازی کامل حافظه GPU (`geometry.dispose()`, `lineMaterial.dispose()`, `renderer.dispose()`) در زمان Unmount.

---

### ج) تحلیل کامپوننت‌های سمت کلاینت و سرور (Client vs Server Component Audit)
1. **لایه ریشه (`app/layout.tsx`):** به صورت Server Component اجرا می‌شود، اما کامپوننت `Providers` به صورت `'use client'` تعریف شده و ابزارهای Global App Loader، SmoothScroll، CustomCursor و ScrollProgress را لود می‌کند.
2. **صفحات سمت کلاینت (`'use client'`):**
   - صفحه اصلی (`(shop)/page.tsx`)
   - کاتالوگ محصولات (`(shop)/products/page.tsx`)
   - سبد خرید (`(shop)/cart/page.tsx`)
3. **صفحات سمت سرور (`Server Component`):**
   - صفحه جزئیات محصول (`(shop)/products/[slug]/page.tsx`): داده‌های متادیتا و آبجکت محصول مستقیماً در لایه سرور از API دریافت شده و ساختار اسکیما و سئوی بهینه بدون وابستگی به رندر کلاینت تولید می‌شود.
4. **فرصت‌های معماری آینده:** کاتالوگ و ساختار هدر و فوتر پتانسیل تبدیل اسکلت اصلی به Server Component با جزایر کلاینتی تعاملی (Interactive Client Islands) را دارند.

---

### د) تحلیل دریافت داده و وضعیت شبکه (Data Fetching & Network Audit)
1. **وضعیت کوئری‌های هدر (`Navbar.tsx`):**
   - در زمان بارگذاری هر صفحه، ۳ کوئری کلاینتی (`cartApi.getCart`، `categoriesApi.getTree` و `promotionsApi.getActivePromotions`) به صورت همزمان ارسال می‌شوند.
   - زمان `staleTime` برای سبد خرید ۳۰ ثانیه و برای دسته‌بندی‌ها و پروموشن‌ها ۵ دقیقه تنظیم شده است که از فراخوانی مکرر و نامناسب پیشگیری می‌کند.
2. **آبشار درخواست‌ها (Request Waterfalls):** در صفحات کاتالوگ، ابتدا اسکلت صفحه لود شده و سپس فراخوانی محصولات انجام می‌شود؛ این فرآیند مانع از تعلیق کامل رندر استاتیک می‌گردد.

### هـ) تحلیل تصاویر و رسانه‌ها (Image Performance Audit)
1. **پروکسی و بازنویسی تصاویر پروداکشن:** تصاویر ذخیره‌شده در بک‌اند از طریق روت بازنویسی `/media/:path*` با هدر `image/jpeg` و کد وضعیت ۲۰۰ با موفقیت تحویل داده می‌شوند.
2. **تصویر شاخص LCP در صفحه محصول (`matrix-falling-code-7680x4320-13665.jpg`):**
   - فایل خام منبع دارای ابعاد خارق‌العاده `7680x4320` پیکسل با حجم **6.97 MB** است.
   - بهینه‌ساز Next.js (`/_next/image`) آن را در ابعاد ریسپانسیو و با کیفیت وب پردازش می‌کند؛ با این حال، بارگذاری اولیه فایل‌های بسیار بزرگ در بک‌اند بدون کش مقدماتی بر زمان پاسخگویی اولین درخواست اثرگذار است.
3. **استفاده از `next/image`:** در `ProductCard` و `ProductGallery` از کامپوننت بهینه `next/image` با پراپرتی‌های `fill`, `sizes` و تعیین هدفمند `priority` استفاده شده است.

## ۹. نقشه راه اولویت‌بندی‌شده بهینه‌سازی (Roadmap for Next Phases)

1. **فاز ۱ — بهینه‌سازی هوشمند انیمیشن‌های اولیه (LCP & Animation Optimization):**
   - حذف حالت اولیه `opacity: 0` از المان‌های بالای خط تا (Above-the-fold) مانند عنوان اصلی صفحه و کارت‌های اول محصولات.
   - جایگزینی انیمیشن‌های جاوااسکریپتی مبتنی بر اسکرول در بخش‌های اولیه هیرو با ترنزیشن‌های CSS خالص و ترکیب‌پذیر (Composited CSS Transitions).
2. **فاز ۲ — بهینه‌سازی خط لوله مدیا و تصاویر (Media Pipeline):**
   - پیش‌تولید اندازه‌های استاندارد و فرمت‌های WebP/AVIF در زمان آپلود محصول در بک‌اند.
   - اضافه کردن هدرهای کش دائمی (Long-term Caching Headers) برای مدیا در Nginx.
3. **فاز ۳ — بارگذاری تنبل افکت‌های جانبی (Lazy Enhancements):**
   - موکول کردن اجرای اسکریپت‌های `CustomCursor` و `SmoothScroll` به بعد از بارگذاری کامل محتوای اصلی (`requestIdleCallback`).

3. **عدم دور زدن منطق سمت سرور:** محاسبات قیمت، اعتبارسنجی سبد خرید و قوانین امنیتی هرگز نباید برای سرعت بخشیدن ظاهری به کلاینت منتقل شوند.
