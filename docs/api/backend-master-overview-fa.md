# مستند جامع و مرجع فنی معماری بک‌اند فروشگاه پارادوکس (Paradox Shop)

این سند مرجع رسمی و نهایی معماری، قابلیت‌های مهندسی، قراردادهای ارتباطی (API Contracts)، پردازش‌های ناهمگام (Async & Celery) و راهنمای تحویل بک‌اند به تیم فرانت‌اند برای پروژه **Paradox Shop** است. تمامی بخش‌های این سند منطبق بر پیاده‌سازی واقعی و کدهای موجود در مخزن پروژه تدوین شده‌اند.

---

## ۱. معرفی پروژه

### ۱.۱. هدف و دامنه عملکردی
پروژه **Paradox Shop** یک پلتفرم فروشگاهی مدرن، مقیاس‌پذیر و مبتنی بر استانداردهای سازمانی (Production-Ready) است. بخش بک‌اند وظیفه مدیریت کامل داده‌ها، فرآیندهای خرید، احراز هویت امن کاربران، انبارداری همگام، ثبت تراکنش‌های پرداخت، و سیستم صف وظایف ناهمگام را بر عهده دارد.

### ۱.۲. وضعیت فعلی معماری
فاز پیاده‌سازی لایه منطق کسب‌وکار (Business Logic)، پایگاه داده، احراز هویت، اعتبارسنجی‌ها و سیستم پردازش‌های پس‌زمینه (Celery & Redis) با موفقیت کامل پیاده‌سازی و با ۵۷ تست یکپارچه (Integration Tests) در محیط Docker ایزوله تثبیت شده است. این سند مرجع اتصال و قرارداد نهایی بک‌اند با لایه فرانت‌اند (Next.js) است.

---

## ۲. معماری سیستم

پروژه به صورت یک **Modular Monolith** طراحی شده است تا ضمن حفظ سادگی نگهداری و دیپلوی، تفکیک کامل دامنه‌ها (Separation of Concerns) و استقلال منطق تجاری را تضمین کند.

```
[ Frontend (Next.js) ]
         │ (HTTP / JSON / JWT)
         ▼
[ Nginx / API Gateway ]
         │
         ▼
[ Django REST Framework (DRF) ]
         │
    ┌────┴────────────────────────┐
    ▼                             ▼
[ Domain Services ]         [ Task Dispatch ]
    │ (Atomic Transactions)       │ (transaction.on_commit)
    ▼                             ▼
[ Selectors / Models ]      [ Redis Message Broker ]
    │                             │
    ▼                             ▼
[ PostgreSQL 16 ]           [ Celery Worker & Beat ]
```

### اجزای اصلی پشته نرم‌افزاری (Tech Stack)
* **زبان و فریم‌ورک اصلی:** Python 3.12+ / Django 5.2 / Django REST Framework 3.15
* **پایگاه داده رابطه‌ای:** PostgreSQL 16 (با تراکنش‌های اتمیک، قفل‌گذاری سطری و محدودیت‌های یکپارچگی)
* **صف پیام و کش:** Redis 7 (پایگاه‌های تفکیک‌شده برای کش، بروکر سلری و نتایج)
* **پردازش ناهمگام و زمان‌بندی وظایف:** Celery 5.6 به همراه Celery Beat
* **مستندسازی API:** OpenAPI 3.0 از طریق `drf-spectacular`
* **احراز هویت:** JWT با `djangorestframework-simplejwt` و مکانیزم چرخش توکن (Token Rotation & Blacklist)
* **کانتینرسازی:** Docker و Docker Compose

## ۳. ساختار کد و لایه‌بندی (Clean Layered Architecture)

کد در هر ماژول دامنه (Domain App) بر اساس لایه‌بندی زیر تفکیک شده است:

| لایه | وظیفه | محل قرارگیری |
| :--- | :--- | :--- |
| **Models** | تعریف شِمای دیتابیس، روابط، ایندکس‌ها، CheckConstraintها و فیلدهای سیستمی | `apps/<domain>/models.py` |
| **Serializers** | سریال‌سازی و اعتبارسنجی داده‌های ورودی/خروجی HTTP و مستندسازی OpenAPI | `apps/<domain>/serializers.py` |
| **Views / ViewSets** | لایه HTTP، مدیریت Permissions، Throttling و فراخوانی سرویس‌ها یا سلکتورها | `apps/<domain>/views.py` |
| **Services** | قلب منطق کسب‌وکار؛ تراکنش‌های اتمیک (`@transaction.atomic`)، تغییرات وضعیت، قفل‌گذاری سطری | `apps/<domain>/services.py` |
| **Selectors** | کوئری‌های بهینه دیتابیس برای لایه نمایش؛ جلوگیری از N+1 (`select_related`, `prefetch_related`) | `apps/<domain>/selectors.py` |
| **Permissions** | کلاس‌های دسترسی اختصاصی (مانند `IsOwner`, `IsOrderOwner`) | `apps/<domain>/permissions.py` |
| **Tasks** | وظایف ناهمگام پس‌زمینه و وظایف زمان‌بندی‌شده Celery Beat | `apps/<domain>/tasks.py` |
| **Common** | مدل‌های پایه (UUID, Timestamp, SoftDelete)، لاگینگ، میدل‌ویر Request-ID و هندلر خطای استاندارد | `common/` |

## ۴. مستندات جامع دامنه‌های هفت‌گانه (7 Domains)

### ۱. دامنه کاربران و احراز هویت (`apps.users`)
* **مسئولیت:** ثبت نام، ورود با ایمیل، خروج (Blacklist)، تغییر رمز عبور، پروفایل کاربر و مدیریت چند آدرسی.
* **مدل‌های کلیدی:**
  * `User`: کلید اصلی UUID، فیلد یکتا `email` به عنوان شناسه ورود، `SoftDeleteMixin`.
  * `UserProfile`: پروفایل متصل One-to-One با کد ملی، جنسیت، وضعیت تایید ایمیل و شماره تماس.
  * `Address`: آدرس‌های کاربر با قابلیت تعیین آدرس پیش‌فرض خودکار و حذف نرم (`is_deleted`).
* **سرویس‌ها:** `UserService` (ثبت‌نام با هش امن رمز و ارسال ناهمگام ایمیل خوش‌آمدگویی، تغییر پسورد، خروج)، `AddressService` (مدیریت یکتایی آدرس پیش‌فرض).
* **سلکتورها:** `UserSelector`, `AddressSelector`.
* **قوانین کلیدی:** فقط کاربر مالک می‌تواند آدرس‌های خود را مشاهده، ویرایش یا حذف کند. ایمیل شناسه اصلی است.

### ۲. دامنه دسته‌بندی‌ها (`apps.categories`)
* **مسئولیت:** مدیریت درخت سلسله‌مراتبی دسته‌بندی‌ها و تعریف ویژگی‌های داینامیک محصول.
* **مدل‌های کلیدی:**
  * `Category`: فیلدهای `parent` (خودارجاعی با `PROTECT`)، `slug`، `sort_order`.
  * `CategoryAttribute`: مشخصه‌های متغیر یا فیلترشونده (Text, Number, Boolean, Select) متصل به دسته.
* **سلکتورها:** `CategorySelector` (ساخت درخت درختی سلسله‌مراتبی در حافظه با ۱ کوئری بهینه).
* **قوانین کلیدی:** مشاهده دسته‌ها برای عموم آزاد است. امکان حذف دسته دارای فرزند مجاز نیست.

### ۳. دامنه محصولات و تنوع‌ها (`apps.products`)
* **مسئولیت:** کاتالوگ محصولات، برندها، تنوع‌های قیمتی/موجودی (ProductVariant)، تصاویر و مشخصات فنی.
* **مدل‌های کلیدی:**
  * `Brand`: برند محصول.
  * `Product`: محصول پایه با فیلدهای `base_price` (ریال)، `is_active`، `is_featured`، `product_type`.
  * `ProductVariant`: تنوع کالا شامل `sku` یکتا، `price_override`، `stock` (موجودی انبار)، `attributes` (JSON). دارای پروپرتی `final_price`.
  * `ProductImage`: گالری تصاویر متصل به محصول و تنوع با اولویت تصویر اصلی (`is_primary`).
  * `ProductAttributeValue`: مقادیر واقعی مشخصات داینامیک.
* **سلکتورها:** `ProductSelector` (فیلتر بر اساس دسته، جستجو در عنوان/توضیحات، بهینه‌سازی شده با `select_related` و `prefetch_related`).

### ۴. دامنه سبد خرید (`apps.cart`)
* **مسئولیت:** سبد خرید برای کاربران احراز هویت شده و کاربران مهمان (Guest Sessions)، افزودن، ویرایش تعداد و ادغام سبد.
* **مدل‌های کلیدی:**
  * `Cart`: کلید `user` (nullable) یا `session_key` (nullable, unique).
  * `CartItem`: اتصال به محصول و واریانت، `quantity` (حداقل ۱)، `unit_price` (اسنپ‌شات لحظه‌ای قیمت).
* **سرویس‌ها:** `CartService` (مدیریت سبد و `merge_guest_cart` با قفل‌گذاری سطری در هنگام ورود)، `CartItemService` (افزودن و ویرایش تعداد کالا با اعتبارسنجی سروری موجودی انبار).
* **وظایف پس‌زمینه:** `cleanup_abandoned_guest_carts` (حذف خودکار سبدهای مهمان غیرفعال قدیمی‌تر از ۷ روز).

### ۵. دامنه سفارش‌ها (`apps.orders`)
* **مسئولیت:** ماشین وضعیت سفارش، تسویه‌حساب (Checkout) اتمیک، اسنپ‌شات‌های قیمت و آدرس، کسر و بازگشت موجودی، لغو سفارش.
* **مدل‌های کلیدی:**
  * `Order`: شامل `order_number` (یکتا با فرمت `PDX-YYYYMMDD-XXXXXX`)، ماشین وضعیت (`PENDING`, `PROCESSING`, `SHIPPED`, `DELIVERED`, `CANCELLED`, `REFUNDED`)، مبالغ `subtotal`, `shipping_cost`, `total`, زمان‌های `paid_at`, `cancelled_at`.
  * `OrderItem`: اسنپ‌شات تغییرناپذیر محصول، نام واریانت، SKU، تعداد، قیمت واحد و قیمت کل در لحظه خرید.
  * `OrderAddress`: اسنپ‌شات تغییرناپذیر آدرس تحویل گیرنده.
* **سرویس‌ها:**
  * `OrderService.create_order_from_cart`: اجرای اتمیک فرآیند چک‌اوت، قفل‌گذاری روی واریانت‌ها (`select_for_update`)، اعتبارسنجی موجودی، **کسر موجودی انبار**، ثبت سفارش و اسنپ‌شات‌ها، پاکسازی سبد خرید، و ارسال تسک ناهمگام ایمیل تایید.
  * `OrderService.cancel_order`: لغو سفارش در وضعیت PENDING یا PROCESSING، **بازگشت اتمیک موجودی انبار به واریانت‌ها**، ثبت `cancelled_at` و تغییر وضعیت به CANCELLED.
* **وظایف پس‌زمینه:** `cancel_stale_pending_orders` (لغو دوره‌ای سفارش‌های پرداخت‌نشده با عمر بیش از ۳۰ دقیقه و بازگردانی موجودی).

### ۶. دامنه پرداخت‌ها (`apps.payments`)
* **مسئولیت:** شبیه‌سازی تراکنش پرداخت، جلوگیری از پرداخت تکراری با Idempotency Key، ثبت شماره تراکنش و ارسال اعلان.
* **مدل‌های کلیدی:**
  * `Payment`: وضعیت‌های (`PENDING`, `PROCESSING`, `SUCCEEDED`, `FAILED`, `REFUNDED`)، `amount` (ریال)، `gateway`، `transaction_id` (یکتا)، `idempotency_key` (یکتا)، `gateway_response` (JSON).
* **سرویس‌ها:** `PaymentService.create_mock_payment` (قفل‌گذاری روی سفارش، بررسی وضعیت PENDING، ثبت تراکنش شبیه‌سازی‌شده، ارتقای وضعیت سفارش به PROCESSING، ثبت `paid_at` و ارسال اعلان ناهمگام رسید پرداخت).

### ۷. دامنه نظرات و امتیازدهی (`apps.reviews`)
* **مسئولیت:** ثبت نظر و امتیاز (۱ تا ۵) برای محصولات، اعتبارسنجی خرید تاییدشده (Verified Purchase)، تایید ادمین (`is_approved`).
* **مدل‌های کلیدی:**
  * `Review`: `rating` (CheckConstraint بین ۱ تا ۵)، `is_verified_purchase`، `is_approved`، `unique_together` روی محصول و کاربر (هر کاربر یک نظر برای هر محصول).
* **سلکتورها:** `ReviewSelector.get_product_reviews` (فقط نظرات تاییدشده نمایش عمومی دارند).

## ۶. قابلیت‌های مهندسی پیشرفته (Engineering Highlights)

### ۱. تراکنش‌های اتمیک و کنترل همروندی (Concurrency & `select_for_update`)
* کلیه عملیات‌های تغییر وضعیت حساس (چک‌اوت، پرداخت، لغو سفارش، ادغام سبد خرید) درون بلاک `@transaction.atomic` اجرا می‌شوند.
* برای جلوگیری از رفتارهای غیرهمگام (Race Conditions) و اضافه فروشی (Overselling)، ردیف‌های `ProductVariant` و `Cart` با متد `select_for_update()` پیش از بررسی و تغییر موجودی قفل می‌شوند.

### ۲. حفاظت از یکپارچگی انبار (Inventory Safety Rules)
* **کسر موجودی:** در لحظه ثبت سفارش (`PENDING`) موجودی واریانت‌ها کسر می‌شود.
* **بازگشت موجودی:** موجودی **تنها و تنها زمانی** بازگردانده می‌شود که سفارش لغو شود (`OrderService.cancel_order`). سرویس لغو به عنوان تنها مسیر معتبر و قطعی لغو در کل سامانه عمل می‌کند.

### ۳. پایداری در برابر تکرار و اجرای مکرر (Idempotency)
* تسک‌های دوره‌ای و تراکنش‌های پرداخت دارای مکانیزم‌های کامل Idempotency هستند. اجرای چندباره وظیفه لغو سفارش‌های منقضی‌شده، به هیچ عنوان موجودی کالا را بیش از یک بار افزایش نمی‌دهد.

### ۴. جلوگیری از N+1 Query
* در لایه Selectors، با بهره‌گیری استراتژیک از `select_related` برای کلیدهای خارجی تک‌مقداری و `prefetch_related` برای روابط چندتایی، تمام کوئری‌های واکشی اقلام و مشخصات در حداقل کوئری‌های بهینه بهینه شده‌اند.

### ۵. اسنپ‌شات‌های تغییرناپذیر تاریخچه (Historical Snapshots)
* تغییر قیمت یا نام محصول و واریانت در آینده هیچ تاثیری بر سفارش‌های گذشته نخواهد داشت؛ چراکه تمامی قیمت‌ها، نام‌ها، SKU و آدرس خریدار به صورت مستقل در `OrderItem` و `OrderAddress` کپی و ایزوله شده‌اند.

### ۶. لاگینگ ساختاریافته و همبستگی شناسه درخواست (Request ID Correlation)
* میدل‌ویر `RequestIDMiddleware` برای هر درخواست یک UUID تولید و در هدر پاسخ (`X-Request-ID`) بازمی‌گرداند. لاگر اختصاصی این شناسه را در تمامی لاگ‌ها درج می‌کند تا اشکال‌زدایی در محیط پروداکشن به سادگی میسر باشد. همچنین فیلتر `SensitiveDataFilter` از ثبت گذرواژه‌ها و توکن‌ها در لاگ جلوگیری می‌کند.

## ۸. سیستم پرداخت (Payment Status: Mock Gateway)

* **وضعیت فعلی:** پیاده‌سازی سرویس پرداخت به صورت **Mock Payment Engine** است.
* **قابلیت‌ها:** اعتبارسنجی وضعیت مجاز سفارش، اعتبارسنجی کلید `idempotency_key`، تولید شناسه تراکنش یکتا (`MOCK-TXN-...`)، تغییر اتمیک وضعیت سفارش به `PROCESSING` و ثبت زمان پرداخت `paid_at`.
* **توجه برای اتصال درگاه واقعی:** جهت اتصال به درگاه‌های واقعی نظیر زرین‌پال یا به‌پرداخت در فازهای آینده، معماری سرویس `PaymentService` کاملا ماژولار بوده و کافی است آداپتور درگاه جدید به عنوان کلاس ارائه‌دهنده اضافه گردد.

## ۹. راهنمای اتصال و تحویل به فرانت‌اند (Frontend Contract & Handoff)

### ۱. آدرس‌های پایه و مستندات زنده
* **API Base URL:** `http://localhost:8000/api/v1/`
* **Swagger UI:** `http://localhost:8000/api/docs/swagger/`
* **Redoc:** `http://localhost:8000/api/docs/redoc/`
* **OpenAPI Schema (JSON):** `http://localhost:8000/api/schema/`

### ۲. چرخه احراز هویت با JWT (Auth Lifecycle)
1. **ورود:** درخواست `POST /api/v1/users/login/` با بدنه `{"email": "...", "password": "..."}`.
2. **پاسخ:** دریافت توکن‌های `access` و `refresh`.
3. **ارسال در درخواست‌ها:** ارسال هدر استاندارد در کلیه درخواست‌های نیازمند احراز هویت:
   ```http
   Authorization: Bearer <access_token>
   ```
4. **تمدید توکن:** در صورت انقضای Access Token (کد خطای 401 با کد `token_not_valid`)، درخواست `POST /api/v1/users/login/refresh/` با بدنه `{"refresh": "<refresh_token>"}` ارسال شود.
5. **خروج:** درخواست `POST /api/v1/users/logout/` با بدنه `{"refresh": "<refresh_token>"}`.

### ۳. ساختار استاندارد صفحه‌بندی (Pagination Schema)
پاسخ اندپوینت‌های لیست دارای ساختار زیر است:
```json
{
  "count": 42,
  "next": "http://localhost:8000/api/v1/products/?page=2",
  "previous": null,
  "results": [ ... ]
}
```

### ۴. ساختار استاندارد خطاها (Error Schema)
در صورت بروز خطای اعتبارسنجی (400) یا خطاهای سیستمی:
```json
{
  "code": "validation_error",
  "detail": "Input validation failed.",
  "errors": {
    "email": ["User with this email address already exists."],
    "stock": ["Only 2 unit(s) are currently in stock."]
  },
  "request_id": "c6a2b8e1-931b-4d69-a1b4-7d5fa24b5e28"
}
```
