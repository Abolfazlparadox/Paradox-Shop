## ۱. چرخه کامل یک درخواست HTTP (Request Lifecycle)

بیایید یک سناریوی روزمره را ردگیری کنیم: **کاربر می‌خواهد یک نظر (Review) برای محصول خریداری‌شده ثبت کند.**

```text
[کاربر روی دکمه "ثبت نظر" کلیک می‌کند]
                 ↓
[۱. کامپوننت فرانت‌اند: ProductReviews.tsx]
   - اعتبارسنجی اولیه فرم در کلاینت
   - فراخوانی هوک useMutation در React Query
                 ↓
[۲. کلاینت HTTP: apiClient در lib/api/client.ts]
   - تزریق اکسس‌توکن JWT در هدر Authorization
   - تولید و الصاق شناسه یکتای ردیابی X-Request-ID
   - ارسال به آدرس POST /api/v1/reviews/create/
                 ↓
[۳. وب‌سرور و روتینگ بک‌اند: api/v1/urls.py]
   - میدل‌ور RequestIDMiddleware شناسه را خوانده و در لاگ‌ها ست می‌کند.
   - روت به CreateReviewView در apps/reviews/views.py هدایت می‌شود.
                 ↓
[۴. لایه کنترل دسترسی و اعتبارسنجی: Serializers]
   - بررسی پرمیشن IsAuthenticated: آیا کاربر لاگین است؟
   - بررسی CreateReviewSerializer: آیا امتیاز بین ۱ تا ۵ است؟ آیا عنوان خالی نیست؟
                 ↓
[۵. لایه منطق تجاری: ReviewService در services.py]
   - فراخوانی ReviewSelector.user_has_purchased_product:
     آیا این کاربر این محصول را در یک سفارش DELIVERED خریداری کرده است؟ (قانون قطعی خرید)
   - آیا کاربر قبلاً برای این محصول نظری ثبت نکرده است؟
                 ↓
[۶. لایه تراکنش پایگاه داده: Django ORM + PostgreSQL]
   - ذخیره رکورد در جدول Review با وضعیت اولیه PENDING.
   - ذخیره تصاویر در جدول ReviewImage.
                 ↓
[۷. فرآیند ناهمگام در پس‌زمینه: Celery + Redis]
   - صدا زدن process_review_image_task.delay(image_id):
     ارسال تسک به ردیس تا بدون مسدود کردن کاربر، تصاویر فشرده و EXIF آنها حذف شود.
                 ↓
[۸. ارسال پاسخ به کلاینت: HTTP 201 Created]
   - سریالایز کردن اطلاعات نظر ثبت‌شده و بازگرداندن به فرانت‌اند.
                 ↓
[۹. بازخورد در رابط کاربری: TanStack Query + UI]
   - نمایش پیام موفقیت با کامپوننت Toast.
   - بی‌اعتبار کردن کش React Query برای کوئری ['product-reviews'] تا لیست بروز شود.
```

## ۲. احراز هویت و امنیت نشست‌ها (Authentication & Token Lifecycle)

در پارادوکس شاپ، امنیت احراز هویت بر مبنای استاندارد **JSON Web Token (JWT)** با الگوریتم HMAC-SHA256 پیاده‌سازی شده است:

### ۲.۱. جفت‌توکن‌ها (Access & Refresh Tokens)
1. **Access Token**:
   - عمر کوتاه: **۱۵ دقیقه**.
   - شامل فیلدهای `user_id`، `email` و زمان انقضا (`exp`).
   - در هر درخواست در هدر `Authorization: Bearer <token>` ارسال می‌شود.
2. **Refresh Token**:
   - عمر طولانی: **۷ روز**.
   - در دیتابیس با ماژول `rest_framework_simplejwt.token_blacklist` ثبت می‌شود.
   - هنگام خروج کاربر (`/api/v1/users/logout/`)، رفرش‌توکن به بلک‌لیست اضافه می‌شود تا دیگر نتوان از آن استفاده کرد.

### ۲.۲. قفل همزمانی تمدید توکن در فرانت‌اند (Concurrency-Safe Refresh Lock)
اگر کاربر ۵ تب مرورگر را همزمان باز کند و اکسس‌توکن منقضی شده باشد:
- کلاینت Axios در `frontend/src/lib/api/client.ts` اولین درخواست منقضی را شناسایی کرده و متغیر `isRefreshing = true` را ست می‌کند.
- ۴ درخواست دیگر در آرایه `failedQueue` به حالت انتظار درمی‌آیند.
- یک درخواست به `/users/login/refresh/` فرستاده می‌شود.
- به محض دریافت توکن جدید، تمام درخواست‌های صف با توکن جدید به صورت خودکار تکرار می‌شوند (`retry`). هیچ اروری به کاربر نشان داده نمی‌شود!

## ۳. تفکیک لایه‌ها در جنگو: چرا Service و Selector؟

در کدهای غیرحرفه‌ای، معمولاً تمام کدهای دیتابیس در `views.py` نوشته می‌شوند که باعث تولید فایل‌های ۳۰۰۰ خطی ناخوانا (Fat Views) می‌شود. در پارادوکس شاپ تفکیک وظایف زیر رعایت شده است:

```text
               ┌────────────────────────┐
               │    HTTP Request        │
               └───────────┬────────────┘
                           ▼
               ┌────────────────────────┐
               │    View (urls/views)   │ ← صرفاً کنترل پروتکل و تبدیل داده
               └───────────┬────────────┘
                           ▼
               ┌────────────────────────┐
               │  Serializer (DRF)      │ ← اعتبارسنجی نوع فیلدها و فرمت ورودی
               └───────────┬────────────┘
                           ▼
          ┌────────────────┴────────────────┐
          ▼                                 ▼
┌──────────────────┐              ┌──────────────────┐
│  Service Layer   │              │  Selector Layer  │
│  (Write / Logic) │              │  (Read-Only Qs)  │
│  تغییر دیتابیس   │              │  خواندن بهینه    │
│  تراکنش‌های اتمیک │              │  بدون خطای N+1   │
└─────────┬────────┘              └────────┬─────────┘
          │                                │
          └────────────────┬───────────────┘
                           ▼
               ┌────────────────────────┐
               │  Database (PostgreSQL) │
               └────────────────────────┘
```

### مثال عینی از پروژه:
- **نوشتن داده**: `OrderService.create_order_from_cart` در `apps/orders/services.py` وظیفه کسر موجودی و ثبت سفارش را در یک بلوک `transaction.atomic()` دارد.
- **خواندن داده**: `ProductSelector.get_filtered_products` در `apps/products/selectors.py` با دستورات `select_related('brand', 'category')` و `prefetch_related('images')` تمام داده‌های لازم برای ۲۰ محصول صفحه اول را تنها با **۲ کوئری SQL** دریافت می‌کند، در حالی که کد ناآگاهانه می‌توانست به ازای هر محصول ۱۰ کوئری اضافی (خطای فاجعه‌بار N+1) اجرا کند.

## ۴. همزمانی و جلوگیری از Race Condition

فرض کنید یک محصول لوکس تنها **۱ عدد** در انبار موجودی دارد و دو کاربر دقیقاً در یک میلی‌ثانیه دکمه «خرید نهایی» را می‌زنند. چطور مانع از فروش یک کالا به دو نفر می‌شویم؟

در `apps/orders/services.py`:
```python
# قفل کردن سطر در سطح موتور دیتابیس تا زمان پایان تراکنش
variant = ProductVariant.objects.select_for_update().get(id=variant_id)

if variant.stock < requested_quantity:
    raise ValidationError("Insufficient stock available.")

variant.stock -= requested_quantity
variant.save()
```
با دستور `select_for_update()`، کاربر دوم پشت قفل دیتابیس صبر می‌کند تا تراکنش کاربر اول تمام شود؛ سپس متوجه می‌شود موجودی ۰ شده و خطای موجودی دریافت می‌کند. هیچ کسر منفی در انبار رخ نخواهد داد.

## ۵. فرآیندهای پس‌زمینه (Celery & Redis)

چرا وب‌سرور نباید ایمیل بفرستد یا تصاویر را ریسایز کند؟  
پاسخ: وب‌سرور باید در کمتر از ۱۰۰ میلی‌ثانیه پاسخ HTTP را به کلاینت برگرداند. ارسال ایمیل ممکن است ۲ تا ۵ ثانیه زمان ببرد و در ترافیک بالا وب‌سرور دچار خفگی شود.

- **تولیدکننده (Producer)**: جنگو پیام را به Redis می‌فرستد:
  ```python
  process_review_image_task.delay(review_image.id)
  ```
- **واسطه (Broker)**: دیتابیس Redis پیام را در صف نگه می‌دارد.
- **مصرف‌کننده (Consumer)**: پروسس `celery_worker` پیام را از صف برداشته، تصویر را با کتابخانه Pillow به وب‌پی تبدیل می‌کند و ذخیره می‌نماید.
- **زمان‌بند (Celery Beat)**: ساعت دقیق را چک می‌کند و هر ۵ دقیقه تسک پاکسازی سفارش‌های معلق را فعال می‌سازد.

## ۶. فرانت‌اند: مدیریت وضعیت سرور در برابر وضعیت کلاینت

در فرانت‌اند پارادوکس شاپ دو نوع وضعیت کاملاً تفکیک شده‌اند:

1. **وضعیت کلاینت (UI State) → Zustand**:
   - وضعیت باز/بسته بودن سبد خرید کناری (`CartDrawer`).
   - وضعیت مودال ورود و ثبت‌نام (`AuthModal`).
   - کلیدهای سشن مهمان و استیت توکن‌ها (`authStore`).
   - بسیار سبک، سینکرون و بدون درگیری با کشینگ شبکه.

2. **وضعیت سرور (Server State) → TanStack Query (React Query)**:
   - اطلاعات محصولات، لیست نظرات، لیست سفارشات.
   - دارای قابلیت‌های پیشرفته: کشینگ هوشمند، به‌روزرسانی در پس‌زمینه (Background Refetching)، مدیریت وضعیت‌های `isLoading` و `isError` و لغو درخواست‌های قدیمی.

## ۷. تست‌های خودکار: اطمینان از سلامت سیستم

در این پروژه **۱۹۰ تست خودکار** تضمین‌کننده پایداری سیستم هستند:
- **تست‌های بک‌اند (Pytest - 139 تست)**: تست ترنزکشن‌های اتمیک، بررسی محاسبه صحیح تخفیف‌ها، تست عدم دسترسی کاربران به سفارشات یکدیگر (IDOR Prevention)، تست ریت‌لیمیتینگ OTP و سیستم نظرات خریداران قطعی.
- **تست‌های فرانت‌اند (Vitest - 51 تست)**: تست تایم‌لاین مراحل سفارش، لاجیک گارد ادمین و تبدیل شاخص‌های KPI به نمودارهای SVG.

برای اجرای تست‌ها:
```bash
# تست‌های بک‌اند در کانتینر
pytest

# تست‌های فرانت‌اند
npm test -- --run
```
